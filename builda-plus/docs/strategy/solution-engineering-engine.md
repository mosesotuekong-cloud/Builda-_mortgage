> [Outlook follow-up drafts spec](../engineering/outlook-follow-up-drafts-spec.md).** Tier C and the

Status: strategy proposal, **revision 2**. Adds the template / reference-solution / bespoke split
(§5.0) and the full document-chasing template deliverable (§10). Part of the
[product direction](builda-product-direction.md).

Turns a validated opportunity into the **right kind of solution**: a fix, a redesign, an
automation, or nothing. It then produces an engineering pack that a JADA engineer can review,
estimate and build from without repeating discovery.

**Boundary (brief §15, unchanged):** builda+ doesn't generate code, execute automation, or connect
to firm systems. Engineering review is a human-controlled gate.

## 2. Entry criteria: when solution engineering starts

A solution is generated only for an opportunity that is:

1. **Approved** by the firm lead as a priority (the `priority_approvals` / `approve` flow);
2. **Classified** with the classification confirmed by the firm lead (or an unchanged AI/playbook
   proposal the firm lead accepted through validation);
3. Supported by evidence at **Medium or higher** for a two-week build proposal. *Low*-confidence
   opportunities can get a **solution brief** (§4) but not a build proposal, and the open questions
   say what evidence is missing.

---

## 3. Solution approach by classification

| Classification | Solution output | Commercial route |
|---|---|---|
| **Fix** | **Process fix brief:** the change (a checklist, owner, template letter or handoff rule), who does what, how to tell if it worked | Fix sprint (fixed price, days, not weeks) |
| **Overhaul** | **Redesign brief:** current vs target process (tasks and roles), dependencies, regulated boundaries, phasing; automation candidates *after* redesign | Scoped redesign engagement |
| **Automate** | Template match → **two-week build pack** if the gates pass; otherwise a **solution brief** for a later phase | Two-week build / later phase |
| **Keep human** | **No automation.** Optionally a support option (prepare information for the person, reduce admin around the judgement), only if a card's pattern says so | Usually none; that's the honest answer |

The fix brief and redesign brief use the same deterministic assembly as the pack (evidence + pattern
+ checks + open questions), with patterns from the knowledge layer. This is a small extension of
`buildImplementationPack`, which today rejects anything not classified `automate`.

## 4. AI versus conventional automation

The brief: *"must not recommend AI or automation simply because it can."* The evolved direction
asks "whether AI is genuinely appropriate". That decision is **deterministic**, from attributes
captured in evidence and the pattern:

| Question | If yes → |
|---|---|
| Does the task involve regulated judgement (suitability, affordability judgement, protection advice)? | Keep human; at most "prepare information for the adviser" |
| Can a simpler process fix remove most of the work (a cause matched by a fix pattern)? | Fix first; automation is reconsidered after |
| Are inputs structured (statuses, dates, checklists, fields in a system)? | **Conventional workflow automation** (rules, schedules, templates). No LLM |
| Is the output a client or third-party communication? | Human approval step is mandatory (template invariant) |
| Are inputs unstructured text or documents that must be read (emails, PDFs, notes)? | **LLM-assisted extraction or drafting with human review**, and only if the error tolerance allows review of every output |
| Would an error change a client outcome or a regulated record without review? | Not eligible for automation in the two-week model |
| Is volume too low to justify it (below the card's threshold)? | Fix or no action |

Outcome categories, recorded on the solution with the rule path that led there:

1. `no_change`
2. `process_fix`
3. `conventional_automation`
4. `llm_assisted_with_review`
5. `not_eligible`

Document chasing, the first template, is **conventional automation**: a status-driven schedule,
approved templates and staff approval. An LLM isn't needed. That's a useful honest signal to the
market.

## 5. Technical architecture recommendations

The evolved direction asks for architecture and technology recommendations. Generic LLM-written
architectures are what the brief warns against. Instead, solutions come in three kinds that are
clearly distinguished, then a reference library (§5.1) and a control set (§5.2).

### 5.0 Templates, reference solutions and bespoke engineering

| | **Tested template** | **Reference solution** | **Bespoke engineering** |
|---|---|---|---|
| What it is | A reference solution built, tested and proven for a specific integration tier, with a fixed spec, test suite and delivery plan | A reusable solution *pattern*: components, data flow, controls and access needs, but not yet a tested build | A solution for a problem no pattern fits, or an integration no pattern supports |
| Who designs it | Already designed; the engineer configures it | Pattern from the library; the engineer adapts and designs the firm-specific parts | The engineer designs it from scratch |
| What builda+ generates | **Two-week build pack** (deterministic) | **Reference-solution pack** (deterministic): the pattern specialised with firm evidence, plus the gaps listed as engineer tasks | **Engineering brief** (deterministic): problem, evidence, constraints, controls, nearest patterns considered and why they don't fit, open questions |
| Two-week eligible? | Yes, if all gates pass | **No.** It becomes a scoped build. The first such build can fund turning the pattern into a template | No |
| Estimate | Standard, adjusted by tier | Engineer estimate, with a range | Engineer estimate after a short design spike |
| Commercial route | Fixed-price two-week build | Scoped build ("template development engagement") | Bespoke engagement, or decline |

**How the route is chosen (deterministic):**
1. An opportunity's pattern (from the card, or confirmed by the engineer) has a **tested template**
   for the firm's integration tier → template route.
2. Otherwise, a reference solution covers the pattern **and** the inventory shows a supported access
   method → reference-solution route.
3. Otherwise → bespoke route.

**What counts as bespoke, and stays bespoke:** firm-specific rules no pattern expresses; a
system with no API or export that would need a new adapter; work spanning several workflows; anything
needing changes to the firm's core systems.

**When bespoke work becomes reusable (template investment rule):** a pattern seen as a validated
opportunity in **≥ 3 firms**, or reference-solution builds **≥ 2**, goes onto JADA's template
roadmap. The evidence is aggregate counts from discoveries (no firm data), plus engineering-review
outcomes. This turns individual engagements into repeatable products.

**The LLM's role in bespoke work:** none in builda+ outputs. Engineers may use AI tools in their own
design work. Anything that enters a pack is engineer-authored and marked as such.

### 5.1 Reference solutions (JADA-owned, versioned knowledge)

A small library of **reference solutions**, each attached to a template or pattern, for example:

| Reference | Shape | Used by |
|---|---|---|
| RS1 Approved-message workflow | Trigger (CRM status via API / scheduled export / manual flag) → work queue → draft from a firm-approved template → staff approval → send from the firm's mailbox → log case reference only → kill switch | Document chasing; status updates |
| RS2 Intake checklist and tracker | A shared checklist per case type, owner per item, stalled-case list. Often a *fix*, no automation | Document collection; fact-find completeness |
| RS3 Assisted re-keying | Pre-filled submission checklist from the CRM export, human check of every field before submission | Application re-keying |

Each reference solution specifies its **components, data flow, access requirements by system
category, and the control set** (§5.2). JADA engineering owns it, and it's reviewed and versioned
like templates.

### 5.2 Control set (attached to every reference solution)

| Control | Requirement |
|---|---|
| Data minimisation | Client data stays in the firm's systems; the automation stores case references only |
| Human approval | Every client or third-party communication and every record change is approved by staff |
| Auditability | Every action is logged with who approved it and when |
| Kill switch | One switch turns it off; tested before go-live |
| Access | Least privilege, read-only where possible, credentials in the firm's or JADA's secret store, never in packs or reports (brief §10) |
| Regulatory | Applicable approved checks are listed with citations; regulated stages need compliance sign-off before build |
| Consumer Duty | Client communication templates are reviewed for clarity and fair treatment by the firm before go-live |
| Data protection | DPIA screening question answered; a DPIA is needed if new processing of client personal data is introduced |
| LLM use (category 4 only) | No client data to the model unless the firm's DPIA and provider terms allow it; output is always reviewed; prompts and versions logged |

### 5.3 Selection

Code selects the reference solution from the pattern and template, then specialises it with
**firm evidence**: the systems named, the inventory access methods, volumes, roles, approval
points, and the firm's rules. Anything that doesn't fit becomes an **open question for the
engineer**. It isn't filled in by the LLM.

## 6. Integration requirements

These come from the technology inventory, deterministically:

| Inventory says (for a system the solution needs) | Pack says |
|---|---|
| API available | "Read access via API: confirm credentials and scope on day one" |
| Export only | "Scheduled export: agree format and frequency; adds delay" (a standard risk in the template) |
| Manual only | "No automated access: staff flag cases manually, or the solution isn't two-week eligible" |
| Unknown | Open question, and the two-week gate "access ready on day one" can't be pre-confirmed |
| Requires changing the system | Fails the two-week gate "no changes to core systems" → later phase |

## 8. Engineering validation (human gate, exists; extend)

1. The engineer picks up the discovery (an audited assignment).
2. Reviews the pack and answers the feasibility checks (exists).
3. **Enters an estimate** (effort and cost) and confirms the reference solution, or records why
   another is needed (new).
4. Code decides `confirmed` / `needs_changes` from the checks (exists). The engineer can't override
   the gates, only answer them.
5. A confirmed review produces the **build proposal**: scope, timeline (two weeks from the date
   access and prerequisites are ready, per brief §7), cost, payback, success measures.
6. Review outcomes feed back:
   - recurring failures → template improvements;
   - recurring open questions → interview questions or cards (through the reviewed knowledge path).

**Template lifecycle:**

| Stage | Meaning | Set by |
|---|---|---|
| `draft` | Spec exists | JADA engineer |
| `tested` | All template test cases pass in a sandbox with dummy data; human approval and kill switch verified. **Tested status is per integration tier/adapter** (§10.3): "tested for Tier C" doesn't make it tested for a given CRM API | JADA engineering lead (only they can set it; two-week eligibility depends on it) |
| `field_proven` | ≥ 2 live implementations with a measured reduction | Engineering lead; the reduction basis changes from *Assumption* to *measured, n implementations* |

`document_chasing_v1` exists as a spec in `src/knowledge/templates.ts` (`tested: false`, reduction

> **Correction to the existing spec text.** `templates.ts` says "the automation keeps only a case
> reference". It can't send reminders without the client's email address and first name. The honest

> instance, deleted 30 days after the case leaves the sequence; logs hold case references only.*

### 10.1 Workflow boundaries

**Starts when** a case manager marks a case as *awaiting documents* with a checklist of outstanding
items (from the firm-approved document list).

**Ends when** one of these happens:
- every item is marked received by staff;
- the case manager stops or closes the sequence;
- the client replies (the sequence pauses and the case manager is notified);
- the final reminder gets no response (the case is handed to the case manager for a call);
- the case is withdrawn or completed.

| In scope | Out of scope (stays with people, or a later phase) |
|---|---|
| Drafting reminders from firm-approved templates that list only the outstanding items | **Deciding which documents a client needs** (the case manager sets the checklist; lender criteria involve judgement) |
| A reminder schedule in business days (bank holidays, quiet hours) | **Checking whether a document is acceptable** (keep human) |
| A staff approval queue (per reminder or batch) | Reading or storing document contents |
| Pausing on reply; handing over after the final reminder; a weekly stalled-cases list | Building a client upload portal (use the firm's existing portal or email) |
| An audit log; a kill switch | Lender conditions after offer, protection documents (later patterns) |
| Templates versioned, with re-approval on change | SMS or WhatsApp (later; consent and PECR review first) |

### 10.2 Required inputs and integrations

| Input | Source |
|---|---|
| Firm-approved document list (by case type) | Firm, agreed during setup |
| Reminder templates (initial request, reminders, final notice) | Drafted by JADA from the firm's wording, approved by the firm's named approver (and the network, if an AR firm, where the network requires approval of client communications) |
| Schedule (e.g. day 0 / 3 / 7 / 10, then hand back) | Firm |
| Named approvers | Firm |
| Case data per case: case reference, case type, client first name and email, outstanding items | Depends on the integration tier (§10.3) |
| Sending mailbox | The firm's shared mailbox on its email platform (Microsoft 365 or Google Workspace), so messages come from the firm's domain and threads stay in the firm's systems |

### 10.3 Integration tiers (tested separately)

| Tier | How case data arrives | "Received" marking | Setup | First to test? |
|---|---|---|---|---|
| **C: standalone** | The case manager enters the case in the automation's small UI (about a minute; the checklist comes from the firm's document list) | In the UI | Mailbox access only | **Yes.** Works with any CRM; fastest to qualify the two-week gate |
| **B: export-driven** | A scheduled export from the CRM (cases awaiting documents, outstanding items) dropped into an agreed secure location | Export or UI | Export configuration + mailbox | **Yes**, a second test, same build |
| **A: CRM adapter** | Read through the CRM's API | Via API (write-back only with confirmation) | Per-CRM adapter | Later, per customer CRM (each adapter tested on its own) |

Tier C adds a small manual entry step, which is re-keying of its own. The adoption metric and the
net time saved (§10.9) show honestly whether it pays off. Tier B removes the step where exports exist.

### 10.4 Human approval requirements

1. **Templates:** the firm's named approver approves every template version before use. Any edit
   creates a new version that needs re-approval. Network approval is obtained where required.
2. **Every send:** in this template version, staff approve each reminder or a batch (one daily
   queue) before anything is sent. Nothing is sent automatically.
3. **Record changes:** the automation never changes the CRM. In Tier A, write-back (for example
   marking an item received) needs staff confirmation.
4. **Exceptions:** client replies, bounces and anything unusual go to the case manager. The
   automation doesn't interpret reply content.
5. **Pause:** a pause per case and a firm-wide kill switch, available to any approver.

(A later "standing approval" option, where pre-approved templates send on schedule without
per-message approval, would need the firm's written sign-off, a compliance view, and a clean
record of at least 4 weeks. It's not part of v1.)

### 10.5 Security and compliance

| Area | Requirement |
|---|---|
| Hosting | Single-tenant instance per firm, UK/EU hosting, encrypted at rest and in transit |
| Access | Mailbox permission limited to the one shared mailbox (the email platform's application-scoping controls); Tier B read access to the export location only; Tier A read-only API scopes |
| Identity | Firm staff sign in with MFA (the firm's identity provider where available) |
| Secrets | In a secret store; never in packs, reports or logs |
| Data minimisation | Stored: case reference, case type, client first name and email, item labels, status, timestamps. Not stored: documents, addresses, financial details |
| Retention | Case data deleted 30 days after the case leaves the sequence; audit log (case ref, template version, approver, timestamps) kept 12 months or as the firm specifies |
| Logs | Case references only, verified by test |
| Contracts | Article 28 data processing agreement between the firm (controller) and JADA (processor); the firm's DPIA, supported by JADA's template DPIA pack; records of processing |
| Consumer Duty | Templates in plain language: what's needed, why, how to send it, who to contact, and help for anyone who is struggling. No pressure wording. Reviewed by the firm (and the network if AR) |
| Vulnerability and complaints | No automated content analysis. Case managers can pause any case; replies always go to a person |
| PECR | Service messages only. Templates can't contain marketing; the template approval checklist enforces this |
| Deliverability | The firm's domain authentication (SPF/DKIM/DMARC) checked before go-live |
| Regulated stages | Documents isn't a regulated-judgement stage, but document *adequacy* is a human judgement (an approved check cites this) |

### 10.6 Testing requirements (to reach `tested` per tier)

| Group | Tests |
|---|---|
| Functional (existing spec cases) | Draft, not send · received items drop out · reply pauses · hand back after the final reminder · rejected draft isn't sent and is logged · no client data in logs |
| Functional (added) | Business days and bank holidays respected · withdrawn or closed case stops the sequence · no duplicate reminders on re-sync · bounce → case manager notified · template change forces re-approval · the kill switch stops all sends within one minute · per-case pause · approval by a non-approver is rejected · recipient comes from case data only (no free-typed addresses at send time) |
| Tier B | Malformed or partial export is rejected without sends · a case missing from the next export pauses rather than resends · re-run is idempotent |
| Security | Mailbox scope can't send from or read other mailboxes · role checks on the approval UI · secrets absent from logs · retention deletion verified · dependency and vulnerability scan · pen test before the first live deployment |
| Operational | Deliverability check on the firm's domain · load at 2× the firm's daily volume |
| Acceptance | UAT with the firm's case manager on dummy cases · one week live on a pilot group with **100% approval and 0 unapproved sends** |

The `tested` flag (per tier) is set by the JADA engineering lead once the functional, security and
tier groups pass in a sandbox with dummy data. Acceptance testing happens per firm.

### 10.7 Implementation scope: the two-week build

**Before the clock starts** (brief §7: the clock starts when prerequisites are ready):
- named approver(s);
- mailbox access granted;
- document list and draft templates agreed;
- tier chosen (C or B), with the export agreed for B;
- pilot group of cases chosen;
- DPA signed;
- the firm's DPIA screening done;
- **baseline recorded** (from discovery evidence, ideally plus a one-week chase tally by case
  managers).

| Days | Work |
|---|---|
| 1–2 | Provision the firm instance; mailbox scoping; Tier B export ingestion if used |
| 3–4 | Configure the document list, schedule and templates; first approval round |
| 5–6 | Run the full test suite on the firm's configuration with dummy cases |
| 7 | UAT with the case manager; fixes |
| 8 | Template final approval (and network, if AR); go-live on the pilot group |
| 9 | Live monitoring: approval queue, deliverability, replies |
| 10 | Handover: user guide, switch-off procedure, support route, measurement plan confirmed |

### 10.8 Definition of done

- all template tests pass on the firm's configuration;
- the firm's approver has signed off the final templates (and the network, where required);
- live on the pilot group with **zero unapproved sends** and every reminder logged with its approver;
- the kill switch and per-case pause have been demonstrated to the firm;
- the baseline is recorded and the success measures and adoption criterion are declared
  (pre-registered);
- the DPA is signed and the retention configuration has been verified;
- the handover note, support route and switch-off procedure have been delivered.

### 10.9 Expected measurable outcomes (pre-registered; never promised as figures in advance)

| Level | Measure | Source |
|---|---|---|
| Adoption | Share of new *awaiting documents* cases in the pilot group enrolled in the flow (threshold agreed with the firm, e.g. ≥ 70% over 4 weeks) | Automation log |
| Control | Unapproved sends = 0; rejection rate of drafts | Automation log |
| Mechanism | Manual chases per case; case-manager active chasing minutes per application (net of Tier C entry time) | Chase tally / pulse interview, before vs after |
| Outcome | Monthly case-manager hours recovered (labelled capacity, not cash) | Derived by code from the mechanism measures × volume |
| Outcome (if case data exists) | Elapsed days in *awaiting documents* | Case milestone data, before vs after (Release 2) |

The 50% reduction in the current spec stays labelled **Assumption** in every builda+ output until the
template is `field_proven` (≥ 2 measured implementations). Proposals show the firm's own baseline and
its agreed target, never the template's assumed reduction as a forecast.

### 10.10 Commercial packaging (for the business to price)

- **Two-week build** (fixed price, Tier C or B).
- **Run and support** (monthly): hosting, monitoring, template changes. This is a natural seed for
  the brief's "ongoing optimisation" layer.
- **Tier A adapter** for a specific CRM: a one-off add-on, reused for every later firm on that CRM.

### 10.11 Next templates (candidates, by expected recurrence)

1. **Case status updates** to clients, introducers and solicitors: the same reference solution (RS1),
   triggered by milestones.
2. **Intake checklist and tracker** (RS2): often a *fix* rather than automation, sold as a fix sprint.
3. **Assisted re-keying** (RS3): high value, but CRM- and lender-portal-specific, so likely
   reference-solution or bespoke for some time.

Order is confirmed by the template investment rule (§5.0) once pilots produce data.
